## H3. 大きい動画（100MB級）を上げられる — ✅ 通った（要修正点あり）

`ffmpeg -fs 105M` で約100MB（105,230,157バイト）の動画を作り、2つの状況で試した。

1. 既定の上限（`MAX_UPLOAD_MB=200`）で100MBを上げる → `200`。3.86秒で完走し、`width=1920`・`height=1080`・`durationMs=41912` が正しく取れた。
2. 上限を絞って挙動を見る（`MAX_UPLOAD_MB=5`）で同じ100MBを上げる → `500`、本文は `{"error":"File too large"}`。

(2)について、上限は確かに機能して大きいファイルを拒否している。ただし返ってきたのは `500`（サーバエラー）で、メッセージも英語のままである。他のAPIのバリデーションエラー（例: パスワード8文字未満なら `400` + 「パスワードは8文字以上にしてください」）と比べて扱いが揃っていない。これは `src/routes/api.js` の `upload = multer(...)` がスローするエラーを、`asyncRoute` や個別のcatchで受けずにExpressの汎用エラーハンドラ（`src/index.js` の `app.use((err, req, res, next) => ...)`）まで素通りしていることが原因と見立てる。修正案は末尾の「src/へ回す不具合」に書く。

## H5. 一覧のクエリに索引が使われている — ✅ 通った（要注記）

H1で1万件を投入したデータベースに対し、`EXPLAIN QUERY PLAN` を実行した。

```
-- date=絞り込み（例: date = '2026-06-01'）
SEARCH c USING INDEX idx_cuts_log_taken (log_id=?)
SEARCH u USING INDEX sqlite_autoindex_users_1 (id=?)

-- 絞り込みなし
SEARCH c USING INDEX idx_cuts_log_taken (log_id=?)
SEARCH u USING INDEX sqlite_autoindex_users_1 (id=?)

-- from/to絞り込み
SEARCH c USING INDEX idx_cuts_log_date (log_id=? AND local_date>? AND local_date<?)
SEARCH u USING INDEX sqlite_autoindex_users_1 (id=?)
USE TEMP B-TREE FOR ORDER BY
```

索引は使われているが、**`date=`（単一日）の絞り込みと絞り込みなしの一覧は `idx_cuts_log_date` ではなく `idx_cuts_log_taken` を使っている**。これはSQLiteのプランナが、`ORDER BY c.taken_at ASC` を並べ替えなしで満たせる `idx_cuts_log_taken(log_id, taken_at)` を優先しているためで、`local_date` の一致判定は索引を使わず行ごとの確認になる（`log_id` で絞られた範囲の中でのスキャンなので、今回の1ログ1万件では実測15〜17msと十分速い）。逆に `from/to`（範囲）の絞り込みでは `idx_cuts_log_date` が使われるが、この索引は `taken_at` の順序を持たないため `USE TEMP B-TREE FOR ORDER BY`（並べ替えの追加コスト）が発生している。

つまり、`idx_cuts_log_date` は「範囲での絞り込み」でのみ使われ、「単一日の絞り込み」と「絞り込みなし」では実質使われていない。1ログあたりのカット数が今回の1万件を大きく超える運用（例えば数十万件）になった場合、`date=` の絞り込みが `log_id` だけでは十分に絞れず、性能劣化する可能性がある。今回の規模では問題にならなかったため判定は✅としたが、**末尾の「src/へ回す不具合」に改善案を書く。**

## src/ へ回すべき不具合と直し方の案

`src/` の修正はしていない（今回の担当範囲外）。見つかった2点と、再現手順・直し方の案を記す。

### 1. アップロード上限を超えたとき、`500` + 英語メッセージで返る（H3）

- **再現手順**: `MAX_UPLOAD_MB` を小さくして起動し（例: `MAX_UPLOAD_MB=5`）、それより大きいファイルを `POST /api/logs/:logId/cuts` へ送る。`500`、本文 `{"error":"File too large"}` が返る。
- **原因**: `src/routes/api.js` の `upload.single('file')`（`multer`）が `LIMIT_FILE_SIZE` エラーを投げると、`asyncRoute` を経由せずExpressの汎用エラーハンドラ（`src/index.js`）まで届き、`err.status` が無いため `500` になり、`err.message`（英語）がそのまま返る。
- **直し方の案**: `createCut` の手前、または個別のルートで `upload.single('file')` をラップし、`err.code === 'LIMIT_FILE_SIZE'` のときは `400`（または `413`）＋日本語メッセージ（例:「ファイルが大きすぎます（上限 ${config.media.maxUploadMb}MB）」）を返す形にする。他のAPIのバリデーションエラー（`400` + 日本語文）と揃える。

### 2. `idx_cuts_log_date` が、`date=`（単一日）の絞り込みでは使われない（H5）

- **再現手順**: 1つのログへカットを大量に投入し、`EXPLAIN QUERY PLAN SELECT ... WHERE log_id = ? AND local_date = ? ORDER BY taken_at ASC` を見る。`idx_cuts_log_taken` が使われ、`local_date` の一致は索引を経由しない。
- **原因**: SQLiteのプランナが `ORDER BY taken_at` を並べ替えなしで満たせる `idx_cuts_log_taken` を、`local_date` を絞れる `idx_cuts_log_date` より優先して選んでいる。
- **直し方の案（どちらか、または両方）**:
  - `idx_cuts_log_date` を `(log_id, local_date, taken_at)` の複合索引にし、`local_date` の一致とその中での `taken_at` の順序を1つの索引で両方満たせるようにする。
  - 1ログあたりのカット数が数万件を超える運用を想定するなら、投入前に一度この形でベンチマークを取り、実際に効果が出るかを確かめてから直す（現状の1万件規模では実害が出ていないため、優先度は高くない）。

## 追加したテスト（`tests/`）

回帰を防ぐため、以下を追加した。

- `tests/render-photo-only.test.js`: 写真だけのまとめ動画が完走し、指定した寸法（`square`→1080x1080）になることを確かめる結合テスト。**今日の回帰ポイント（E8）そのもの**を自動テスト化した。
- `tests/render-job-error.test.js`: `FFMPEG_PATH` を壊した状態でジョブを発注し、`status: error` かつ空でないメッセージが返ることを確かめる結合テスト（E12）。

また、他の担当からの申し送りにより、`tests/api.test.js`・`tests/private-log.test.js`・上記2ファイルの起動待ちを `tests/helpers/server.js` に共通化し、固定10秒でタイムアウトしていた作りを、`healthz` を60秒まで叩き続ける時間ベースの待ちに直した（上限に達したときはサーバの標準出力・標準エラーを添えて落ちるようにした）。`rm -rf node_modules && npm ci` 直後の `npm test` で41件すべて通ることを確認した。
